== 8. FINDINGS AND LIMITATIONS ==
Confirmed:
 F1 The installed Ollama and qwen2.5:7b produce well-formed tool_calls for this application's tool definitions; the application executed six real calls
    (get_task_catalogue, get_technician_availability x3, validate_schedule, lookup_stock), returned actual data or coded errors, stayed within MaxToolCalls,
    and sent the final request in JSON mode without tools.
 F2 Unknown identifiers chosen by the model were rejected with UNKNOWN_WINDOW instead of producing data.
 F3 The model invented a window ID ("2023-10-15T08:00:00Z/2023-10-15T18:00:00Z") and a technician ("T-101"). The interpreter's user prompt does not include
    the request's windowId (it contains the request text, selected asset IDs, asset list and task catalogue), so the model had no way to know
    MW-P101-BASELINE-20261024. This is an implementation gap in the prompt, not a model fault.
 F4 Performance: on CPU-only inference, single requests took 17.8 s to 261.8 s; two exceeded the 180 s per-request timeout, so the job failed
    (OLLAMA_TIMEOUT, transient -> one automatic retry -> exhausted). The tool loop multiplies the number of requests (8 in attempt 2), making timeouts likely.
 F5 As predicted, the proxy cannot see the API give up while Ollama is generating: Ollama finished 0002 and 0010 after the API's timeout
    (outcome client_disconnected), and 0002's generation overlapped the start of attempt 2.
 F6 Business-data and approval boundaries held (section 7); the original database's main file was never touched by the API.
 F7 Side effect caused by the verification itself, not by the application: after the run, a read-only Python sqlite3 open of the ORIGINAL (to read its
    journal mode) created maintenance-planner.db-wal (0 B) and maintenance-planner.db-shm (32768 B) beside it at 11:13:00, because the database is in WAL mode.
    The original's main file is unchanged (sha256/length/lastWrite as recorded). Both files are git-ignored. They were left in place pending the owner's decision.
Not established:
 - Whether a tool-enabled run completes successfully with a faster runtime (GPU) or a longer timeout; whether the final JSON would then pass validation
   (the late 0009/0010 content has all required fields, but it was never parsed by the application).
 - Whether CPU-only inference also caused the slow status responses.
 - Interpretation quality beyond this single request.
